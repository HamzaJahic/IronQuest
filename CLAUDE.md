# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

IronQuest — a gamified workout tracker for a fixed 4-day Upper/Lower split, presented as a themeable "training diary" (three styles × five palettes × light/dark, see Appearance). Offline except the optional **Open Food Facts** product search (meal builder and ingredient calculator; no key, no account): Room database, no accounts; that search is the only network call. An `:app` module plus `:baselineprofile` (Macrobenchmark test module that generates `app/src/main/generated/baselineProfiles/` and benchmarks cold start; it never ships), package `com.ironquest.app`. Also tracks meals ("Food"): a meal library, daily meal plans, quick meals logged food by food ("Log as I go"), and a per-day food/water/supplement log.

## Layering

`UI → ViewModel → (domain rules + repository interfaces) → Offline*Repository → Room`

- **`domain/` is pure Kotlin. It has no Android imports — keep it that way.** This is what lets the game rules and the ViewModels run in plain JVM unit tests with no Robolectric.
- ViewModels depend on the `WorkoutRepository` *interface*, never on `OfflineWorkoutRepository` or on Room types.
- Each ViewModel exposes one `StateFlow<XxxUiState>`. Today and Log build theirs with `combine(...).stateIn(WhileSubscribed(5_000))`; ActiveWorkout owns a `MutableStateFlow` it mutates itself.
- One-shot UI events (XP toast, level-up, snackbar) go through a `Channel` exposed as a `Flow` — see `ActiveWorkoutViewModel.events`. Don't model these as state.
- Screens split into a stateful `XxxScreen(viewModel = hiltViewModel())` and a stateless `XxxContent(state, …)`. **Big screens** (Active workout, Food day, Meal editor, Plan editor, Workout log editor, Import) take one `onAction: (XxxAction) -> Unit` — a sealed `XxxAction` next to the VM, whose only public function is `onAction` (plus `uiState` / `events`); pass it as `remember(viewModel) { viewModel::onAction }` so pages can skip. Navigation and Android side effects (clipboard, SAF, the reminder permission gate) stay plain lambdas in the stateful screen. Small screens keep plain callback lambdas.
- **Domain naming:** `XxxUseCase` only for classes that coordinate repositories (`MealImportUseCase`). Pure rules are `object`s with named functions: `ProgressiveOverloadRules.suggest`, `GoalRules`, `DaySummaryCalculator.summarize`, `NutritionOverviewCalculator`. No pass-through use cases. Live-workout row logic is pure in `domain/workout/` (`WorkoutSession`, `SessionExercise`, `SessionRow`, `SetInput`, superset extensions in `SupersetProgress.kt`).
- `java.time.Clock` is injected (`DatabaseModule.provideClock`, which returns `LiveZoneClock`) so tests can pin "today". Never call `LocalDate.now()` or `System.currentTimeMillis()` directly in domain, repository, or ViewModel code.

## The program lives in code, not the database

`domain/program/ProgramCatalog.kt` is the single source of truth for exercises, the four templates, rep ranges, and the rotation. The `exercises` **table is only a mirror** so that `sets` can have a real foreign key.

`SeedCallback.onOpen` re-upserts the catalog into that table on **every database open**, using `INSERT OR IGNORE` + `UPDATE` — deliberately *not* `INSERT OR REPLACE`, because REPLACE deletes the row first and trips the RESTRICT foreign key from `sets`.

**Consequence: adding or editing an exercise means editing `ProgramCatalog` only. No migration, no DB version bump.**

**Imported programs (CSV, v4)** are the exception: `programs` / `program_days` / `program_exercises` hold user programs, read through `ProgramRepository` (`OfflineProgramRepository`). The built-in split is `Program(id = null)`; exactly one program is active (no `isActive` row = built-in). Everything that needs a template (Today, ActiveWorkout, goal notifications, calendar day log) resolves it via `ProgramRepository.findTemplate` — never `ProgramCatalog.template` directly. Imported day template ids are `"C<dayId>"` (`Program.customTemplateId`); imported exercises not matching a catalog exercise (by name or id) get id `x_<slug>_<hash>` and are inserted once (`INSERT OR IGNORE`, never updated). Built-in days can't be edited; deleting a program is refused while one of its days has an unfinished session, and its history shows as "Deleted program" (resource `log_deleted_program`; the built-in split's display name is resolved by `programName()` in `ui/catalog/CatalogNames.kt`, never by the repository). `CompletedWorkoutLog.templateName` is nullable: null means the template can no longer be resolved, and the UI shows the "Deleted program" / "Workout" fallback text.

**The built-in split can be deleted** (`deleteProgram(null)`): `ProgramCatalog` stays in code (history and `findTemplate` still resolve "Upper 1"), a flag `built_in_program_hidden` in `AppSettingsRepository` hides it, and `restoreBuiltIn()` (button on Programs) brings it back. `observeActiveProgram()` is nullable: with the built-in hidden and no active imported program Today shows "No workout program is active" (`TodayUiState.noProgram`) and the You row says "No active program". Deleting the active program hands over to the newest imported one only while the built-in is hidden; otherwise the built-in is the fallback again. Both deletes are refused while one of the program's days has an unfinished session.

Rotation is Upper 1 → Lower 1 → Upper 2 → Lower 2 → repeat (`nextInRotation`). The first exercise of each template is the "main lift" Today's note line is about. Today's main day is `NextWorkout.pick` (`domain/program/NextWorkout.kt`): an unfinished workout, else the "Do next" choice while active, else `nextInRotation` after `WorkoutRepository.observeLastCompletion()` (template + completion time; replaces `observeLastCompletedTemplateId`). The goal notification uses the same pick.

**Supersets (v5):** `TemplateExercise.supersetGroup` (null = standalone; the built-in catalog has none). `WorkoutBlock.of` / `WorkoutTemplate.blocks` (pure, `domain/model/WorkoutBlock.kt`) splits a day into pages: a run of **consecutive** exercises with the same key is one `Superset`, lettered A, B, … by position (letters are never stored; a run of one stays `Single`). `SupersetRounds` gives the order: round r = set r of each member in order, rounds = the largest set count, shorter members are skipped in later rounds. Stored keys only need to be unique within a day; `addExercises` renames clashing imported keys (`a` → `a~2`, `OfflineProgramRepository.uniqueSupersetKeys`) so they never merge with the day's existing groups.

## Game rules — single source of truth

All of it lives in `domain/progression/` (`LevelCurve.kt`, `XpRules.kt`, `LevelUpDetection.kt` with `detectLevelUp`) and `domain/progression/ProgressiveOverloadRules.kt`. Changing a number in either file will break specific assertions in `ProgressionTest` / `ProgressiveOverloadRulesTest` — that's intended; update the tests deliberately rather than loosening them.

**Progressive overload**, evaluated against the last *completed* session of the same template:

| Rule | Condition | Result |
|---|---|---|
| Level Up | all prescribed sets logged, all at the working (max) weight, all ≥ top of rep range | working weight + `incrementKg` |
| Deload | ≥ 2 sets below bottom of range (and weight > 0) | working weight × 0.9, rounded **down** to 2.5 kg (with an FP epsilon) |
| Hold | everything else, including a single missed set | same weight |

Plus `FirstEncounter` (no history) and `NotApplicable` (cardio).

**XP:** 10 per strength set; cardio is 1 XP per minute with a minimum of 10. +5 "Ghost Slayer" when a set beats the ghost at the same index — (≥ weight AND more reps) OR (more weight AND ≥ reps); lighter-weight-for-more-reps does **not** count. +100 workout completion bonus (`QUEST_COMPLETE_BONUS`), which goes to character XP only. Set XP also feeds the exercise's stat (legs → CON, upper → STR, cycling → STA); stats grow from set XP and goal bonuses only.

**Goals** (replaced quests; `domain/goals/`, pure): `GoalRules.forWorkout(template, lastSetsByExercise)` gives at most one goal per exercise with history — **Limit break** when its overload suggestion is `LevelUp` (done when ≥ `targetSets` sets this session are at ≥ the suggested weight; reps don't matter), otherwise **Beat last time** (done when this session's volume > last session's). **Volume** per set = `weightKg × reps` if weight > 0, else `reps` (bodyweight); cardio = minutes; summed over the exercise's sets. **Food** goals (`forFood`) are the active plan's protein/water targets; they pay nothing extra (the existing +25/+10 stay). Bonuses `XpRules.LIMIT_BREAK_BONUS = 25`, `BEAT_LAST_TIME_BONUS = 10`, paid **once inside `completeWorkout`'s transaction** (`GoalRules.completionAward`: final sets vs the previous completed session of the template, read in the transaction) to character + the exercise's stat, only for goal types passed in `completeWorkout(id, goalTypes)` (the VM passes the types whose **Show** switch is on), included in `workouts.xpEarned` and in level-up detection; `WorkoutCompleteResult.goals` has the breakdown. Completion stays idempotent (a repeat pays nothing).

**Streak** (`domain/progression/WeekStreak`): consecutive Monday–Sunday weeks with completed workouts (by start date, repeats count) ≥ the active program's day count; the current week adds 1 once complete and never breaks it while running; 104 weeks of look-back (`WorkoutRepository.observeCompletedDates`).

**Levels:** character L→L+1 costs `100 + 50·(L−1)`; stats cost `40 + 20·(L−1)`. Cap 999. Character XP can drop (un-logging meals), so `player_profile.highestLevelReached` records the peak: workout `logSet`/`completeWorkout` and nutrition `xpWrite` report a character level-up only above it (`gateLevelUp`, via `reportLevelUp`) and raise it in the same transaction; stat level-ups are always reported.

## Past workouts and sharing plans

- **Log tab day sheet** (`ui/log/`): "Add workout" (days of the active program) → `workoutlog/0/{templateId}/{epochDay}`; each finished workout has Edit / Delete (`workoutlog/{id}/…`, `delete` asks first). `WorkoutLogEditorViewModel` (`ui/workout/`) is a **form**: nothing is written until Save, so there are no half-finished past sessions (unlike the live `ActiveWorkoutViewModel`, which autosaves). Blank rows are dropped, reps/minutes required, empty weight = bodyweight (`parseRow` / `toDraft` are pure companion functions). "Same as last time" copies the ghost; exercises of a deleted/edited day stay editable from the stored sets.
- **`WorkoutRepository.saveWorkoutLog` / `deleteWorkout`** (one transaction each). A new past session is stamped at **noon of its day** (now when the day is today), `startedAt == completedAt` (so no duration), and pays like a live one: set XP with the ghost = latest session that *started before it* (`getLastCompletedBefore`), goal bonuses for the shown goal types, +100, `questsCompleted`++. A rewrite keeps date/times, **re-prices only the sets** and applies the difference (`adjustXp`, floored at 0); the goal bonus it was paid is kept as is. Delete takes back `xpEarned` (character) and each set's XP (its stat) and `questsCompleted`−1; **stat XP from goal bonuses stays** (not stored per stat). Level-ups from these writes are reported to the editor but not shown (the editor just closes).
- **Food needs no new entry screen**: the Day view already steps back to any earlier day (writes allowed up to today), now also by tapping the date (`DayPickerDialog`, days after today not selectable). A past day with no stored row shows the live plan's targets until its first write snapshots them.
- **Plans can all be deleted**: meal plans were already deletable (user data); workout programs now include the built-in split (see above).
- **Export / share** (`domain/importing/CsvExport`, pure): `program(templates)` writes the workout CSV (`day,exercise,sets,…,superset`, supersets as per-day letters), `mealPlan(slots)` the meal-plan CSV incl. tags, recipe URL and recipe; both import back unchanged (`CsvExportTest` round-trips them through the parsers). A meal plan's targets are not exported (the importer sums the meals). UI: "Share" on Programs and Plans cards → `shareText` (system share sheet, plain text); the receiver uses Import → Paste. No file/FileProvider.

- **Erase all data** (You tab, "Your data"; `DataResetRepository.wipeLoggedData`, `WipeDao`): two confirmations, then one transaction deletes workouts (sets cascade), meal logs, nutrition days and supplement intakes and resets the profile (XP, stats, workouts, `highestLevelReached`). Programs, exercises, meals, meal plans, supplements and settings stay; reminders are re-armed afterwards. Not covered by an automated test.

## Backup (save / load your data)

- **You tab → Export & import**: "Export data" (SAF `CreateDocument`, default name `ironquest-backup-<date>.json`) and "Import data" (SAF `OpenDocument`). There is deliberately **no share sheet / FileProvider** for data (plans have their own Share buttons, see Export / share above). The system pickers list Google Drive next to device storage, so **Drive needs no Google sign-in, API key or SDK in the app**; a real Drive API integration would need a Cloud project/OAuth client and is deliberately not built. File helpers: `ui/you/BackupFiles.kt` (reads capped at 50 MB, manual read loop because `readNBytes` is API 33). Importing shows a preview ("Backup from 2026-10-12: 12 workouts…") and a destructive "Import" confirmation before anything is touched.
- **Format** (`domain/backup/`: `BackupFormat.kt`, `BackupTable.kt`, `BackupMigrations.kt`, `BackupData.kt`, …; pure): JSON `{ format: "ironquest-backup", version, appSchemaVersion, exportedAt, settings: { builtInProgramHidden, foodTrackingMode, ownTargets }, tables: { <table>: [ { column: value } ] } }`. Contents: every table in `BackupTable` (workouts, sets, player profile, meals, tags, plans, slots, logs, nutrition days, supplements, intakes, programs, days, program exercises, exercises; since v2 user foods and meal log items). **Not included:** appearance and goal settings, and which tips were seen. `BackupFormat.CURRENT_VERSION` (2) is the *file format* version, independent of the Room version.
- **`OfflineBackupRepository`** dumps/restores generically by column name (`SELECT *`, `PRAGMA table_info`), so a new column or table needs no new code here: columns present in the file are written, missing ones take their SQL default, unknown ones are ignored. Restore = one transaction: `defer_foreign_keys`, delete the replaced tables children-first, insert parents-first (`exercises` only inserted with IGNORE, never deleted; the built-in ones are re-seeded on open), re-create the profile row if absent, then `PRAGMA foreign_key_check`; **any failure rolls back and nothing changes** (`RestoreResult.Failed` with a user-facing message). Never throws.
- **`BackupJson`** (org.json, `opt()` + `as? Number`) decodes; `BackupMigrations.prepare` is the version failsafe: newer-than-app files are refused ("made by a newer version"), older files are upgraded step by step (`steps`; 1 → 2 is an identity step: the two new tables are simply empty in a v1 file), tables newer than the file are treated as empty, other missing tables are reported as an incomplete backup.
- Android's own auto-backup (`allowBackup="true"`) still covers the whole app data to the user's Google account; this feature is the explicit, portable copy.

## Data changes need a failsafe (rule)

Whenever the way data is stored or structured changes, an outdated copy of the data must still load without crashing or losing anything:
1. **Room schema** change → version bump + `Migration` + `MigrationTest` case (see Room schema below). Never use `fallbackToDestructiveMigration`.
2. **Backup content** change (a table or column added, renamed, removed or reinterpreted) → add the table to `BackupTable` (with `since`) and, if old files need converting, bump `BackupFormat.CURRENT_VERSION` and append a step to `BackupMigrations.steps` that turns version N into N+1. Update `BackupFormatTest` (it asserts the table list) and keep a test that loads an old-version file.
3. **Preferences / other stored formats** (SharedPreferences keys, CSV formats) → unknown or missing values fall back to defaults (`enumOrNull`, `getBoolean(key, default)`, `OnboardingSeenCodec` behind `OnboardingRepository`), never throw.
4. Anything reading a file or stored value from outside the running code returns a typed result instead of throwing (see `BackupRepository` with `BackupError`, `ImportParse` with `ImportProblem`); the UI turns it into text.
5. **Translations** must keep every placeholder of the English string (same count, same positional index, same type); `StringResourcesTest` checks this for every `values-xx/` file, plus plurals and edge spaces.

## Food (meal tracking)

Pure rules in `domain/nutrition/` (`NutritionRules`, `DaySummaryCalculator`, `StreakCalculator`); Room access via the `NutritionRepository` interface (`OfflineNutritionRepository`). Spec: `docs/superpowers/specs/2026-10-05-meal-tracking-design.md`.

- **Meals/plans are user data**, unlike exercises: seeded once by `MIGRATION_1_2` (existing installs, frozen English seed) and `SeedCallback.onCreate` (fresh installs) from `NutritionSeed`, never re-upserted on open. `NutritionSeed` reads its meal names and recipes from `strings_seed.xml`, so fresh installs get the device language at install time; after that they are user data and are never re-translated. Plan editor: `PlanEditorAction.AddSlot(defaultLabel)` receives the localized default slot label from the screen; `NutritionRepository.duplicatePlan(id, copyName)` takes a lambda that builds the copy's name from the original (the screen supplies "%s (copy)" from resources).
- A plan is a daily template of slots. **Only one plan is active** (`setActivePlan` clears all, then sets one, in a transaction).
- `meal_logs` snapshot meal name + 1× macros at log time; editing/deleting a meal never rewrites history. Deleting a meal used by a slot **archives** it (`Meal.archived`; `observeArchivedMeals`, `restoreMeal` un-archives); same for supplements with intakes.
- `savePlan` diffs slots and **updates in place** — never delete-and-reinsert, or `SET NULL` turns today's checked slots into off-plan logs.
- **Today reads live targets from the active plan**; `nutrition_days` keeps a snapshot that only matters once the day is past.
- **XP (character only):** +5 per logged meal (planned or off-plan), +25 when the day's protein target is reached, +10 for the water target, +2 per supplement taken. Every write pays/reverses through `xpWrite` → `syncDay` in one transaction; un-logging takes XP back (floored at 0). `updatePortion`/`removeLog` on a missing log return `alreadyDone`. Water per day is clamped to `MAX_WATER_DAY_ML` (10 000) by `NutritionRules.clampWater`.
- Slot/supplement writes are **idempotent in the repository** (`alreadyDone`), because notification actions (phase 3) write outside any ViewModel mutex.
- **Week / Month** (phase 2) read `NutritionRepository.observeHistory(from, to)`: SQL per-day sums (`observeDayTotals`), `nutrition_days` rows, the live active-plan targets and supplement intakes. `NutritionOverviewCalculator` (pure) applies the rules: future days and days with neither a `nutrition_days` row nor logs are **no data**; today uses the live plan, past days their snapshot (same as `observeDay`). Colours (`DayMark.fillColor(colors)`): Under `muted` at 60 %, OnTarget `accent` (±10 %), Over `hold`, no target `line`, no data `line` at 40 %.
- Week = **Monday–Sunday**, one macro at a time (default protein); the dashed `ink` target line is today's live plan target in the current week, otherwise the latest snapshot target. "On target X/Y" counts **logged days** (≥ 1 meal log). Averages are over logged days, water over days with water > 0, supplement adherence over elapsed days on/after the supplement's `createdAtEpochDay` (null = from range start; v3 backfilled it from the first intake). Intake reads are bounded to a 400-day window (`STREAK_WINDOW_DAYS`), so a streak shows at most 400. Month is coloured by protein; streaks are anchored at the last visible day (today or month end).
- Today's food line (`TodayViewModel.buildFoodLine`): protein bar + `NextMeal.pick` (earliest unchecked slot at/after now, else the first unchecked slot in plan order; none → "All meals done"). Tapping it opens the Food tab via `navigateTopLevel` (same options as the bottom bar).
- **Reminders (phase 3).** `ReminderSchedule` (pure, `domain/nutrition/`) turns a `ReminderSnapshot` (active-plan slots, supplements, what's logged/taken; read via `NutritionRepository.reminderSnapshot(from, to)`) + `Clock` into the **next occurrence only** of each reminder (looks `SEARCH_DAYS` = 3 ahead). `targetEpochDay` is the meal/dose date, not the trigger date (00:10 slot − 15 min fires 23:55 the evening before). Supplements have no offset; they fire at `reminderTimeMin`. Request code = `(id shl 1) or kind.ordinal`, also used as the notification id.
- **Re-arm pipeline:** `NutritionRepository` is bound (in `di/ReminderModule.kt`) to `RearmingNutritionRepository`, a `by`-delegating decorator over `OfflineNutritionRepository` that calls `ReminderRearmer.requestRearm()` after savePlan / setActivePlan / deletePlan / logSlot / removeLog / setSupplementTaken / saveSupplement / deleteSupplement. ViewModels know nothing about reminders. `ReminderCoordinator` posts requests to a `Channel(CONFLATED)` drained on the `@ApplicationScope` scope (a burst of writes = one re-arm); receivers call the suspending `rearmNow()` instead. A `Mutex` serializes both. It injects the concrete `OfflineNutritionRepository` on purpose — the interface would be a Dagger cycle. `IronQuestApp.onCreate` creates the channel and re-arms on every process start.
- `ReminderScheduler` (AlarmManager): exact `setExactAndAllowWhileIdle` when `canScheduleExactAlarms()`, else `setAndAllowWhileIdle`. AlarmManager can't list alarms, so armed keys and their trigger times live in SharedPreferences `reminders` — removed slots get cancelled. **Past-due grace:** a stored trigger that is already due but not yet delivered (inexact alarms can be minutes late) is left alone for up to `PENDING_GRACE_MILLIS` (2 h, `ReminderSchedule.keepPending`), so a re-arm in that window doesn't replace today's alarm with tomorrow's. `ReminderReceiver` calls `markFired` first, so the re-arm after delivery moves on.
- Receivers in `notifications/`: `ReminderReceiver` (re-checks with `isStillDue`, posts via `ReminderNotifier` on channel `meal_reminders`, always re-arms in `finally`), `MarkEatenReceiver` (MARK EATEN / TAKEN via `goAsync`), `SafetyRearmReceiver` (exported=false; a daily `setInexactRepeating(INTERVAL_DAY)` alarm that calls `rearmNow()`, armed from `IronQuestApp.onCreate` and `BootReceiver`, no WorkManager), `BootReceiver` (exported; boot, `TIME_SET`, `TIMEZONE_CHANGED`, `MY_PACKAGE_REPLACED`, exact-alarm permission granted). Manifest: `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`.
- Permissions (`ReminderPermissions`, `ui/food/ReminderHints.kt`): `rememberReminderPermissionGate` saves first, then asks for POST_NOTIFICATIONS (API 33+) if a reminder is set. Editors show "Reminders may be late — allow exact alarms" when exact alarms are denied (default on API 34+), and "Notifications are off — reminders won't show" only when notifications are disabled **and** we've already asked (`askedNotificationPermission` pref) or the API is < 33 — never before the user was asked.
- **Goal notifications (redesign phase 2).** `GoalReminderSchedule` (pure, `domain/goals/`) arms the next daily occurrence of WORKOUT (at the workout time, when Limit break or Beat last time is shown + notify) and FOOD (food time, Food shown + notify). Fixed negative request/notification ids (−1001/−1002), so they never meet `ReminderSchedule.requestCode`. `ReminderCoordinator.rearmNow` also applies them (`ReminderScheduler.applyGoals`, same past-due grace, trigger prefs `trigger:goal:*`) and re-arms on every goal-settings change. `GoalReminderReceiver` decides at fire time: workout → skip if a workout was completed today or no notified goals for today's day (same pick as Today (`NextWorkout.pick`, incl. Do next)); food → only the open shown targets. Channel `goals` ("Goals", `GoalNotifier`); tap opens Today (`today`) or Food via `EXTRA_OPEN_ROUTE`.
- **Notification tap → Food Day.** The tap intent carries `EXTRA_OPEN_ROUTE`; `MainActivity` feeds it to `IronQuestNavHost(openRoute, onRouteOpened)`, which navigates like a bottom-bar tap, pops to the Food root (`popBackStack(FOOD, false)`, in case `restoreState` brought back Meals or an editor) and bumps the saveable `foodDayRequest`; `FoodScreen` switches its mode to Day when that counter changes (so rotation afterwards keeps whatever mode the user picked).
- **Clock zone is live (`LiveZoneClock`):** "today" and reminder times follow the device zone (`Clock.systemDefaultZone()` would freeze it at process start, so a `TIMEZONE_CHANGED` re-arm would use the old zone). "Today" can move backwards on a westward zone change; a Day view followed to the later date then rejects writes until `refreshToday()`.
- **Quick meals ("Log as I go")** (spec `docs/superpowers/specs/2026-10-23-quick-food-logging-design.md`, plan `docs/superpowers/plans/2026-10-23-quick-food-logging.md`): one `meal_logs` row (slotId and mealId null, portion 1, macros = sum of its items, name from `QuickMealName` by time of day or typed) plus its foods in `meal_log_items` (CASCADE from the log). Items snapshot name, amount, unit and macros like every log; editing or deleting a food never rewrites them. `NutritionRepository.saveQuickMeal(date, logId, name, items)`: a new meal pays +5 XP like any meal; an edit replaces the items, re-sums the log and pays 0 (the day's protein/water bonus is re-evaluated by `syncDay` as usual). `MealLogEntry.items` / `isQuickMeal`.
- **Meal builder** (`ui/food/builder/`, route `food/log/{epochDay}/{logId}`, logId 0 = new; "+ Log food" on the Food day): name chips, items, search (local after 250 ms; online after 400 ms when the query has ≥ 3 chars and < 5 local hits, else "Search online"), inline `AmountRow` (amount + unit chips + live macros; shared with the ingredient calculator), recents. Picking a library meal with an empty builder logs it off-plan with a portion (`PortionDialog`); with items present it becomes a `MEAL_PORTION` item. "Save as a meal" (saved logs only) copies the total into the library with one recipe line per food. `isSaving` stays true after Done, like the other editors.
- **Foods and units** (`domain/food/`, pure): `FoodUnit` (g / ml / pcs / serving / USDA portion "p:<label>" / meal portion "x"; `storageKey`, unknown → grams), `FoodAmount` (parse with `,`, limits 5 000 g/ml, 100 pieces/servings, `macrosFor`, `startUnit`), `FoodChoice` + `FoodKey` (`b:<usdaId>` built-in, `u:<id>` your food, `m:<id>` library meal), `FoodSearchRanker` (word/prefix/singular scoring), `FoodSearchUseCase` (`local`: library meals, your foods, built-in; `online`; `resolve(key)` re-finds a recent's food, null → its snapshot is used with its one unit).
- **Built-in foods:** `assets/foods/basic_foods.tsv` (~2,500 USDA SR Legacy foods, public domain; header `#ironquest-basic-foods\t1`), generated by `scripts/build-foods.py` from `design/usda/sr_legacy/*.csv` plus the name fixes in `design/usda/names.tsv`. GET `https://world.openfoodfacts.org/cgi/search.pl?search_terms=…&search_simple=1&action=process&json=1&page_size=20&fields=…` through the shared `data/net/HttpTransport` (`HttpUrlConnectionTransport`, headers per request, 8 s connect/read timeouts, body capped at 4 MB). The whole fetch is wrapped in `withTimeout(20_000)` (timeout → OFFLINE), request + parse inside `runInterruptible(Dispatchers.IO)`. **Never throws** (except `CancellationException`): failures are `Result.failure(FoodSearchException(FoodSearchError))` — OFFLINE, RATE_LIMITED (429; about 10 searches a minute), SERVER (other non-2xx), BAD_RESPONSE — with no cause. LRU cache of 32 **successful** queries keyed on trimmed, whitespace-collapsed, lowercased text; a blank query returns empty without a request. No key, no account. Data is ODbL: the builder and calculator show "From Open Food Facts" under online results.

Products with no code or name, or none of P/C/F/energy, are skipped.
- **Ingredient calculator** ("Estimate from ingredients" sheet in `MealEditorScreen`): `IngredientCalculatorViewModel` searches your foods + built-in foods (no library meals) and online with the builder's rules, then the same `AmountRow`; pure `IngredientCalculator` does `IngredientRow(food, unit, amountText)` macros via `FoodAmount`, totals and `applyTo`. The VM is `hiltViewModel()` in the sheet, so it is scoped to the meal-editor back-stack entry.

## Behaviors that look like bugs but aren't

Preserve these unless deliberately changing them:

- **"Do next"** (Today, Other days row): the choice lives in prefs `next_workout_template` / `next_workout_chosen_at` (`NextWorkoutChoiceCodec`), not in backups and not erased. It ends when a workout is completed after it (`completedAtMillis > chosenAtMillis`: a Log entry for today, or for a day whose noon is after the choice, ends it; back-filling an earlier day doesn't; deleting the completion that ended it brings the choice back), when its day leaves the active program, or on `setActiveProgram` (cleared). Do next on the rotation's own day clears it. An unfinished workout wins over it and the choice stays stored underneath. The Today tip's "Do next" step waits for `OnboardingFact.DO_NEXT_VISIBLE` (other days shown and the main day not unfinished), so it never points at a hidden action.
- You-tab sections (`CollapsibleSection`) open and close without animation, on purpose (an animated height moved the whole page). Tabs switch without a transition, also on purpose.
- A past workout added in the Log shows `12:00` as its time and has no duration; editing it never changes date or time. Deleting a workout removes it from the ghost chain, so the next session's "last time" falls back to the one before.

- The `workouts` row is created lazily on the **first logged set**, not on screen open — so opening a workout and backing out leaves no empty session behind.
- `ActiveWorkoutViewModel` guards every write with a `Mutex` (`writeMutex`) so fast double taps can't create two workout rows. Any new write path must go through it.
- The ghost is loaded **once** at screen load via `.first()` and kept as a snapshot, so it can't shift mid-session. "Add set" uses that same snapshot to find ghosts beyond the prescribed set count.
- `logSet` awards XP and updates the profile inside one `db.withTransaction`, and `detectLevelUp` compares snapshots taken *inside* that transaction. `updateSet` (editing an already-logged set) never re-awards XP.
- **Delete set / Restart / Stop** (live workout): the logged-set edit dialog has Delete → `WorkoutRepository.deleteSet` (unfinished sessions only; takes back the set's XP from character + stat, floored at 0; returns true and deletes the workout row when it was the last set, so no empty session is left). The row opens again with the deleted values typed in; an extra set at the end beyond `targetSets` disappears (`SessionExercise.withoutSet`). The header "⋯" (shown once a set is logged) offers Restart workout (`deleteWorkout`, reload, `sessionKey`++ re-keys the pager to page 1) and Stop workout (`deleteWorkout`, `WorkoutEvent.Stopped` → exit), each confirmed. `highestLevelReached` is not lowered, so re-earning a level isn't reported twice.
- `completeWorkout` is idempotent — completing twice pays the bonus once — and refuses to complete a session with zero sets.
- An unfinished session always takes the main slot on Today ("Resume workout"), so resuming is one tap.
- After logging a set, its weight and reps carry forward into the unlogged rows below it, overwriting earlier carries (so the next set starts from the previous one, not the first), and "Add set" copies the last row's (strength only).
- Weight input accepts `,` as a decimal separator; max 1000 kg; 0 kg is valid (bodyweight).
- Calendar days key on the session's **start** date, so a workout past midnight stays on the day it started. Future days aren't selectable and you can't navigate past the current month.
- Returning to Today uses `popBackStack(Routes.TODAY, inclusive = false)`, which is idempotent, so a double tap can't pop Today itself.
- Meal and Plan editors ask "Discard changes?" (BackHandler + top-bar back) when `form != loadedForm` and not saving. Meal delete hands "Meal deleted" / "Meal archived …" to the Meals (or Food) screen via `savedStateHandle["food_message"]`. The meal library has an Archived filter chip; an archived meal's detail shows Restore.
- Food editors (`MealEditorViewModel`, `PlanEditorViewModel`) keep `isSaving = true` after a successful save/delete on purpose, so a second tap during the exit animation can't insert a duplicate.
- `FoodDayViewModel` follows "today" across midnight via `refreshToday()` (called from `LifecycleResumeEffect`) only while the user hasn't navigated to another day. Day-view writes use `uiState.value.date`, never the pending requested date.
- Editing the active plan's targets in `savePlan` re-evaluates today's protein/water bonus. That XP is returned in `SavePlanResult.award`; the editor passes it to the Plans screen through the previous entry's `savedStateHandle` (`food_message` / `food_level_up`), which shows "+N XP"/"−N XP" and the level line ("Level 8 reached") in one snackbar, once.
- Removing a slot that was logged today turns that log into an off-plan log (FK SET NULL); re-adding the slot lets it be logged again. Accepted consequence of the snapshot design.
- `setSupplementTaken` on a deleted supplement, or taking an archived one, is a no-op (`alreadyDone`). `setActivePlan` with a missing id throws instead of leaving zero plans active.
- The water + button (Day view) is disabled at `NutritionRules.MAX_WATER_DAY_ML` (10 000 ml); the repository also clamps. The Day view shows a `reward` bonus tick on the protein bar at 100 % of target and "+25 XP" once reached.
- Plan mode keeps "+ Log something else" (library picker + portion) and has no builder; quick meals logged before a switch to Plan still show (tap to edit, ✕ to remove).
- Recents are read from the logs, so deleting a log removes it from recents. A recent food whose food was deleted adds from its snapshot, with that one unit only.
- Picking an Open Food Facts product saves it to your foods at once (even if you then cancel the amount), so it shows under recents/your foods afterwards and works offline.
- "Log something else" asks for the portion (`PortionDialog`, default 1×) right after picking the meal; the Meal detail "log" button still logs at 1× (edit the portion afterwards).
- Today's "Next" meal is recomputed when today's nutrition data emits, not on a timer, so it can stay on a slot whose time has passed until something changes.
- Food's Day/Week/Month mode is `rememberSaveable` UI state in `FoodScreen`, not ViewModel state. Tapping a Week bar or Month day calls `FoodDayViewModel.showDate` and switches to Day; that day is then not followed across midnight.
- A day with only water/supplements is coloured (usually "under") in Week/Month but is not a "logged day" for averages and on-target counts.
- Week/Month follow "today" only on resume or mode switch (same as Day), not continuously across midnight.
- The Week target line uses today's live plan target in the current week, otherwise the latest snapshot target.
- A reminder that fires the evening before a post-midnight meal has **no "Mark eaten" button** (`canMarkFromShade`) — logging it then would be a future date. Tapping the notification opens Food instead.
- Notification actions pay XP silently (no toast/level-up dialog — there's no UI). Re-arming also removes posted reminders that are no longer due, so checking a slot in the app clears its notification.
- A reminder tap navigates like a bottom-bar tap and pops to the Food root, so an open workout/unsaved editor is left (logged sets are safe; unsaved edits are lost).
- Saving a slot/supplement with a reminder saves first, then asks for POST_NOTIFICATIONS while it isn't granted (the prompt may launch even if the save then fails validation); Android stops showing the prompt after two denials. Force-stopping the app cancels its alarms (Android behaviour) until the next app start.
- Supplement edits write `reminderTimeMin` as given — callers must pass the current value to keep it.
- The calculator's ingredient list survives closing and reopening the sheet (VM scoped to the editor entry); a new editor starts empty.
- Failed lookups are not cached, so retry hits the network again; a repeated successful query works offline from the in-memory cache (lost on process death).
- RATE_LIMITED shows "Online search is busy, try again in a minute."; other online errors show a short unavailable line. Errors never hide local results.
- A 2xx whose body fails to parse (including any runtime exception in `OffParser`) reports BAD_RESPONSE, not OFFLINE; only transport `IOException`s and unexpected exceptions map to OFFLINE.
- Goals on Today and during a workout come from the ghost snapshot; a goal stamps once per session (an edit that undoes it lets it stamp again), and goals a resumed session already met don't stamp. A posted goal notification is not withdrawn when the goal becomes moot (unlike meal reminders).
- **Erase all data** leaves the onboarding tips as they are (D4): tips are a device preference, like appearance. Only You → Appearance → "Show tips again" brings them back, and the You tip itself may then show at once.
- A superseded search is cancelled in the coroutine, but `runInterruptible` can't abort a blocked socket read, so the old thread may linger up to 8 s. Harmless.

## Onboarding (first-visit tips)

The first time you open each feature, a short tip (one to seven steps) shows how it works, as a coach mark over the real control. Plan: `docs/superpowers/plans/2026-10-14-onboarding.md` (decisions D1–D5 at the top; D1 = A+B).

- **The catalogue is the single source of truth:** `domain/onboarding/OnboardingTopic.kt` (pure) lists every tip as an `OnboardingTopic` — the `OnboardingScreen`s it shows on, its `OnboardingStep`s (each with an optional `OnboardingTarget` to highlight and an optional `requires` fact that hides just that step), the topic's `requires` facts, `after` (wait until another topic is seen) and `version`. Declaration order is priority order. Words live in `ui/onboarding/OnboardingCopy` + `strings_onboarding.xml`; the domain has none.
- **Rules** (`OnboardingRules.next`, pure, tested in `OnboardingRulesTest`): nothing while `BLOCKED` is in the facts; a topic without `requires` is an **intro** (first visit of its screen), one with `requires` is **contextual** (when its situation first comes up); **one tip per arrival**: after a tip has shown in a visit, only a contextual tip whose facts appeared *during* that visit may follow, so tips never chain on arrival. A topic is seen when its stored version ≥ `topic.version`.
- **`OnboardingGate(screen, facts)`** goes in the **stateful** `XxxScreen` only, once its state has loaded (facts of the first composition count as "there at visit start"). Facts come from the UiState (pure helpers like `TodayUiState.onboardingFacts()`); `BLOCKED` while the screen's own dialog, sheet, menu or the workout finish summary is up. A visit ends on `ON_STOP` / dispose unless the activity is changing configuration (tabs restore saved state, rotation is the same visit). Delay `IronMotion.TIP_DELAY_MS`.
- **Anchors:** `Modifier.onboardingAnchor(target)` (in `XxxContent`, parameter-free) reports screen bounds **only while that target is wanted** (otherwise a no-op, so scrolling pays nothing) and brings its control into view. One anchor per target (list screens mark the first row). If no bounds arrive within `TIP_ANCHOR_WAIT_MS`, the card centres without a hole. The workout pager provides `LocalOnboardingAnchors` only to the current page.
- **Demos** (`OnboardingDemos.kt`) only where a coach mark can't show it: welcome step 1, the workout swipe step, superset rounds. Built from kit pieces, animated in draw/layer only, `clearAndSetSemantics`, static when the animator scale is 0.
- **Storage:** `OnboardingRepository` → `PrefsOnboardingRepository` (SharedPreferences `onboarding`, keys `seen_<topic>` = version seen; `OnboardingSeenCodec` ignores unknown keys and wrong types). A device preference: **not in backups** (D5), **not touched by Erase all data** (D4). You → Appearance → "Show tips again" resets all (D3: no per-screen replay). Every tip's first step has "Skip all tips".
- **Automation:** `MainActivity` marks everything seen when started with the boolean extra `com.ironquest.app.SKIP_ONBOARDING` (`EXTRA_SKIP_ONBOARDING`); the baseline-profile journeys, `StartupBenchmark` and `scripts/measure-smoothness.sh` pass it, so tips never block scripted taps.

### Adding a feature? Add its tip

1. A new `OnboardingTopic` (or a new step on an existing one), with its screens, targets and any `requires` facts / `after`. Bump `version` when an existing feature changes enough that its tip should show again.
2. Title/body strings in `strings_onboarding.xml` and the mapping in `OnboardingCopy` (`OnboardingCopyTest` fails if a step has no copy).
3. The gate and its facts in the stateful screen (a new `OnboardingScreen` if it's a new screen; `BLOCKED` for the screen's own dialogs).
4. `Modifier.onboardingAnchor(...)` on each targeted control; a demo only if no single control shows it.

## UI conventions

- **Motion (smoothness pass, 2026-10-12, plan `docs/superpowers/plans/2026-10-12-smoothness.md`):** durations live in `ui/theme/IronMotion.kt` only. Tab switches don't animate; pushed screens fade in `SCREEN_FADE_MS` (120 ms) — Navigation's default was a 700 ms cross-fade. Never animate layout size inside a scrolling column (`animateContentSize`, `AnimatedVisibility` with expand): show/hide instantly; animate only through `graphicsLayer { }` with the state read inside the lambda. Draw with `drawWithCache` when a draw needs objects (PathEffect, Path, Brush). Callback bundles passed to many children (e.g. the workout screen's `onAction`) are `remember`ed so pages can skip.
- Icons: `material-icons-core` only. Icons outside it go in `ui/kit/IronIcons.kt`, copied from the material-icons-extended sources; don't add `material-icons-extended` back.
- Release builds shrink resources and keep only the locales in `defaultConfig.resourceConfigurations` (`en` today). Add a locale there with its translation, or its strings are stripped from the APK. Size check: `scripts/measure-size.sh` (profiling APK 2,580,509 bytes after quick food logging (+ the 186 KB food list), 2,441,288 after onboarding, 2,316,640 after refactor phase 2, was 3,074,675; debug APK 11.7 MB, was 24.2 MB).
- **Performance checks** run on the `profiling` build type (`./gradlew installProfiling`, then `adb shell cmd package compile -m speed-profile -f com.ironquest.app`), never on debug. The Pixel_9_Pro_XL AVD renders with SwiftShader (software GPU): its frame stats are only good for before/after comparison.
- **Every colour, font and shape comes from `IronTheme`** (`IronTheme.colors / .type / .shapes / .style`); never hardcode them in screens. Stock M3 widgets (text fields, switches, sheets, dropdowns) pick the palette up through the `MaterialTheme` mapping in `IronTheme`; set `containerColor = colors.raised` on dialogs and sheets.
- One accent per screen. `reward` only for level / XP / goal-done moments; meaning colours (`up`/`hold`/`deload` + `…Bg`) for overload, warnings (`hold`) and errors/destructive actions (`deload`).
- No glow, gradients, `//` labels, monospace or letter-spaced headings, and no card per section: hierarchy comes from type size, rules and whitespace. Lists are `RuledRow`s inside a `RowGroup` (Diary dashed rules, Bold solid top rules, Soft `raised` tiles) — the style decides, screens don't branch on it except for small paddings (`ListTreatment.TILES`).
- Copy is plain, short, second person, sentence case, and lives in `res/values/strings_*.xml` (see i18n), not in code; Bold's upper-casing is applied by the kit (`IronTheme.style.cased`), never by hand. Game words only where they are the feature (Level, XP, Streak, Limit break). No RPG wording ("quest", "slain", "rations") in user-visible strings or notifications; code uses the UI names too (packages `ui/food`, `ui/log`, `ui/imports`; `Food*`, `Log*`). Only storage keeps old names: Room tables and columns (`questsCompleted`), DAO SQL, prefs keys, backup JSON keys, notification channel ids.
- Build screens from `ui/kit/` (see Appearance) before writing new chrome; add a kit piece only when a pattern repeats.
- Raw M3 `AlertDialog`, `ModalBottomSheet`, `OutlinedTextField`, `Switch` and single-`Text` `TextButton`s are only used inside `ui/kit`; screens use the kit pieces. A pattern goes into the kit at its second use.
- Navigation uses **string routes** (`ui/navigation/Routes.kt`), not type-safe routes. Routes: `today` (tab "Today"), `log` ("Log"), `food` ("Food"), `you` ("You"), `workout/{templateId}`, `workoutlog/{workoutId}/{templateId}/{epochDay}` (workoutId 0 = new), `meals`, `meal/{mealId}`, `meal/edit/{mealId}`, `plans`, `plan/edit/{planId}` (`new` creates), `programs`, `import/{kind}` (`ImportKind` name). The bottom bar shows on today, log, food and you; tab routes arriving from notifications posted before the 2026-10-13 rename (`hub`, `chronicle`, `rations`) are mapped by `Routes.fromLegacy`; re-selecting the current tab is a no-op. Pushed screens open via `navigateFrom(entry, route)` (only when the LIVE top entry has `entry.id` and is RESUMED, so double taps can't push twice — compare by id, because a tab restore creates a new entry object while the composition and its remembered callbacks survive; read nav callbacks through `rememberUpdatedState` inside `remember`), go back via `popIfResumed`, and VM-driven exits (Saved/Deleted) use `popIfOnTop` (works even if the user left the app mid-save). `SystemBarIcons` follows `colors.isDark`.
- Row status (EMPTY / READY / LOGGED / DIRTY), the live "beats last time" preview, the stepper maths, carry-forward, add set/round and delete-set row handling are pure in `domain/workout/` (`SessionExercise.statusOf` / `beatsGhost` / `parse` / `withSteppedWeight` / `withLoggedSet` / `withoutSet`, `SetInput`, `WorkoutSession`), tested in `WorkoutSessionTest` / `SetInputTest`. Put new row logic there, not in the ViewModel or the composable.

## i18n (strings and locales)

The English app is fully string-resourced; other languages are added by resource files only. Spec: `docs/superpowers/specs/2026-10-13-refactor-design.md` (Phase 4), plan `docs/superpowers/plans/2026-10-13-refactor-phase-4.md`.

- **Resources** (`app/src/main/res/values/`): `strings_common` (Save, Cancel, units, shared formats), one file per feature (`strings_today`, `_log`, `_food`, `_workout`, `_you`, `_imports`, `_goals`, `_kit`, `_notifications`, `_onboarding`, `_setup`), `strings_catalog` (built-in exercise and day names, keyed by id), `strings_seed` (seeded meals), `strings.xml` (`app_name` only). Keys are `feature_screen_what` in lower snake case (`food_day_water_title`); content descriptions end in `_cd`, plurals in `_count`.
- **Rules for strings:** two or more placeholders are positional (`%1$s`, `%2$d`); a literal `%` is `%%`; apostrophes `\'`; counts are `<plurals>` (at least `one` and `other`); no sentence is built by concatenation. **Edge spaces:** aapt2 trims leading/trailing whitespace of unquoted strings, so a string that starts or ends with a space (`" · "`, `"Superset "`) must be wrapped in double quotes in the XML. `EnglishText` (test fakes) strips one surrounding pair.
- **Date formats** come in two kinds. `DatePatterns` skeletons (`EEEEdMMMM`) go through `DateFormat.getBestDateTimePattern`, so each locale gets its own order and punctuation. Where a screen's English output must stay exactly as it was ("EEEE, d MMMM", "d MMM"), the pattern is a `translatable="false"` string resource (`food_date_long_pattern`, `today_date_long_pattern`, …): `StringResourcesTest` does not require a translation, and a language that needs another order either overrides it in its own `values-xx/` file or the screen moves to a skeleton.
- **`UiText`** (`ui/text/UiText.kt`): `Res` / `Plural` / `Verbatim` (content such as a meal name) / `Joined` (items + translatable separator). ViewModels, `Event.Message`s and pure text builders return `UiText`, never `String`; the screen resolves it with `UiText.resolve()` (composable, re-resolves on locale change) or `resolve(resources)` (snackbar coroutines, notifications at fire time). `failedText(template, error)` wraps an exception message into a "Couldn't …: %1$s" template. Composables use `stringResource` / `pluralStringResource` directly.
- **Domain returns typed values, the UI words them:** `ImportProblem`, `BackupError`, `ProgramProblem` (thrown as `ProgramException`), enums. Copy builders: `ui/goals/GoalCopy` (was `GoalText`), `notifications/ReminderCopy` (was `ReminderText`), `ui/imports/ImportCopy` + `ProgramCopy` (words for `ProgramProblem`), `ui/you/BackupErrorText`, `ui/catalog/CatalogNames` (`exerciseName`, `templateName`, `programName`; imported names show as stored, the DB mirror keeps English).
- **Numbers and dates** go through `ui/format` (`Formats`, `DatePatterns`, locale from `currentLocale()`). **Displayed times follow the device 12/24-hour setting** (`Formats.timeOfDay(minutes, locale, is24Hour)`; `TimeDialog(is24Hour)`). **Files and editor fields stay locale-independent:** `Double.formatAmount()` and `formatKg()` use `Locale.ROOT` on purpose (they feed text fields, CSV and backup), as do CSV column names, the example CSVs, backup JSON keys and the YouTube query. Bold's upper-casing uses the current locale.
- **Checks:** debug builds add the pseudo-locales `en-XA` (accented, every string bracketed: anything unbracketed is hardcoded) and `ar-XB` (right-to-left) through `androidComponents ... aaptAdditionalParameters` in `app/build.gradle.kts`; the release/profiling APK keeps only `en`. Switch with `adb shell cmd locale set-app-locales com.ironquest.app --locales en-XA` (reset with `--locales ""`). `StringResourcesTest` guards key names, positional placeholders, plurals, translation placeholders and edge spaces. `scripts/find-hardcoded-text.sh [paths]` lists literals that look like UI text; a literal that is not UI text carries a `// not UI text: <reason>` marker at the end of its line, or alone on the line directly above the literal (the above-the-literal position is the ktlint-stable one: formatting can move a trailing marker, never this one; the script accepts both) (icon names, Room/SQL names, Open Food Facts query parameters and JSON keys, backup JSON keys, ids, prefs keys); the detector should show only comment lines.
- **Adding a language:** create `values-xx/strings_*.xml` (copy the English files, keep placeholders, add plural forms the language needs), add the locale to `resourceConfigurations` in `app/build.gradle.kts` (`generateLocaleConfig` publishes it to the system's per-app language list), re-run `scripts/subset-fonts.sh` if the script isn't Latin, then run the pseudo-locale and `StringResourcesTest` checks.

## Kotlin conventions

Phase 5 of the refactor programme applied these everywhere; keep them in new code.

- **Names:** no one-letter names for values, variables, function or lambda parameters, `catch` parameters, loop variables or destructured components (`index`, `exercise`, `set`, `row`, `slot`, `error`, `cancellation`, `offsetX`). Generic type parameters (`T`, `K`, `V`, `R`) are fine. `it` only in a single-line lambda whose meaning is obvious (`filter { it.isLogged }`); nested and multi-line lambdas name their parameter.
- **Named literals:** name a positional `true`/`false`/`null` when the function has two or more parameters (`updateRow(id, index, saving = true)`). Skip it for a sole argument, when the function name says it (`setEnabled(false)`), and for Compose / stdlib calls where the name adds nothing (`mutableStateOf(false)`, `getOrNull(0)`).
- **No `!!`** anywhere (main, test, androidTest): use smart casts, `?: return`, `checkNotNull(value) { "why" }` / `requireNotNull`, and in tests `checkNotNull(value)` or restructure the assertion.
- **Expression bodies:** a function whose body is a single `return expr` is written `= expr`.
- **Comments say why**, not what. No section-divider banners and no references to plan history ("phase 3", "spec §4"); KDoc where a type or function needs a contract.
- **One concept per file** (Kotlin's guideline, not one type per file): closely related declarations stay together (a ViewModel with its `UiState` / `Action` / `Event`, a sealed type with its cases, the `IronStyleSpec.kt` enums); unrelated types get their own file in the same package, named after the main type. Imports: sorted, `java.*` / `javax.*` / `kotlin.*` last, no wildcards.
- **Formatting** comes from `.editorconfig` (ktlint 1.5.0 `android_studio` style; the `filename` and `max-line-length` rules are off). Android Studio's *Reformat Code* reads it. Phase 5 applied it with a one-off ktlint CLI run from a scratch binary (`build/tools/ktlint`, not part of the build). If the code drifts, re-run it the same way: `build/tools/ktlint --format "app/src/**/*.kt" "baselineprofile/src/**/*.kt" "!app/src/main/generated/**"`, then check that `scripts/find-hardcoded-text.sh` still shows only comment lines (the `// not UI text` markers sit above their literal for that reason). The build itself still has no lint, Detekt or ktlint; the "don't invoke them" rule above is about Gradle tasks.
- **Locale-safe number pairs:** string resources that put two numbers around a symbol ("4×5–8", `common_range`, the `*_weight_reps` strings) wrap each pair in FSI/PDI isolates written as `\u2068` / `\u2069` escapes, so right-to-left text keeps the order. `EnglishText` (test helper) strips them and resolves plurals (`EnglishPluralsTest`).

## Repo state

Git repository on the owner's **personal** GitHub (`HamzaJahic/IronQuest`, private, branch `main`). The remote uses the SSH alias `github-personal` and the folder gets its personal identity through an `includeIf` in the global git config; never change global git settings (they belong to a work account). Commit or push only when asked. Claude working files (`claudedocs/`, `docs/superpowers/`, `.claude/`, `.superpowers/`) are git-ignored; `CLAUDE.md` is tracked.

**Releases:** pushing a tag `vX.Y.Z` runs `.github/workflows/release.yml`: unit tests, `:app:assembleRelease` signed with the upload key from Actions secrets (`KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS`, `KEY_PASSWORD`), signature check, then a **draft** release with `IronQuest-vX.Y.Z.apk` to publish by hand. `versionName` = X.Y.Z, `versionCode` = X·1 000 000 + Y·1 000 + Z (env `VERSION_NAME` / `VERSION_CODE`; locally 0.1.0 / 1). The key is never in the repo: `app/build.gradle.kts` only signs when `IRONQUEST_KEYSTORE` is set, so local release builds are unsigned. Losing the key means users can't update without uninstalling.
